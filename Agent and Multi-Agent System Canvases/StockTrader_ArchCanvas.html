Multi-Agent Architecture Canvas

StockTrader
StockTrader — Architecture: Market Data → Momentum Trader ∥ Value Contrarian ∥ Volatility Averse → Evaluator (three-way synthesis), using Anthropic Claude Sonnet (`claude-sonnet-4-6`) with plain Python asyncio orchestration
1 Agent Design & Reasoning
1
🧠 Agent Model Strategy
Per Agent Market Data Component: no LLM — deterministic Python computation. Momentum Trader: Anthropic Claude Sonnet (`claude-sonnet-4-6`, Messages API), temperature 0.3. Value Contrarian: same model, same temperature, different system prompt. Volatility Averse: same model; dedicated user prompt foregrounding ATR, σ(returns), worst 1-day drop. Evaluator: same model, three-way comparative synthesis prompt. All four LLM calls per stock use identical model configurations; behavioral divergence comes entirely from prompt design.
Homogeneous Homogeneous by design. Using one model isolates the variable under study: prompt-driven behavioral divergence. If agents used different models, it would be unclear whether output differences stem from the prompt philosophy or from model capability gaps. Anthropic Claude Sonnet is chosen for strong instruction-following and JSON-friendly completions. A heterogeneous setup (e.g., a different model for evaluation vs. strategies) is a valid extension but introduces confounding variables.
Profiling Pre-defined system prompts (prompts/strategy_a.txt, strategy_b.txt, strategy_c.txt, evaluator.txt). Each strategy prompt encodes: behavioral philosophy, explicit decision framework with BUY/HOLD/SELL criteria, ranked data priority hierarchy, an explicit ignore list, a personality bias, and a strict output schema. Prompts are loaded at call time from disk. The third agent uses strategy_c.txt.
2
⚙️ Individual Behavior Implementation
Cognitive Market Data: rule-based deterministic computation — no reasoning, no LLM. Strategy agents: single-shot prompted generation. Each agent receives a system prompt + formatted data in one user message and returns structured JSON in one completion. No ReAct loops, no tool use, no chain-of-thought scaffolding, no multi-turn refinement. Reasoning is embedded in the system prompt's decision framework rather than emergent from a control loop. Evaluator: same single-shot pattern with a comparative synthesis prompt.
Spatial Market Data: yfinance API (read-only). Three strategy agents: Anthropic Messages API (inference only) — no tool access. Each agent receives the same market data dict (Volatility Averse uses a volatility-focused user prompt). Evaluator: Anthropic Messages API — receives all three strategy outputs + market data summary (including ATR, σ). No agent touches the filesystem; JSON writing is handled by the orchestrator.
Temporal Phase 1: Market Data executes first (~1–3s: yfinance + indicators including ATR, 30d/90d σ). Phase 2: Three strategy agents execute concurrently via asyncio.gather (no cross-visibility). Phase 3: Evaluator runs after all three strategies return. Total per-stock wall time: ~8–14s (four LLM calls). Inter-stock delay: 2 seconds. Client uses Anthropic SDK default timeouts unless overridden.
3
⏱️ Temporal Dynamics & Simulation Model
Time model Event-driven batch execution. The system processes a fixed list of tickers sequentially — each ticker is a discrete event. There is no simulated time, no tick-based progression, and no continuous loop. The system runs once, produces outputs, and terminates. Market data represents a historical snapshot (most recent 90–120 trading days), not a live stream.
Sync Within a single stock analysis: the three strategy agents synchronize at a completion barrier — the Evaluator blocks until strategy_a, strategy_b, and strategy_c are available. Implemented via asyncio.gather. Stocks are still processed sequentially with a 2s gap.
Lag effects No intra-run lag effects. The system is stateless between stock analyses — outputs from one ticker do not influence the analysis of another. The only lag is the 2-second inter-stock delay imposed for API rate limiting, which is an infrastructure constraint, not a causal modeling choice. Historical lag effects (e.g., how a 90-day moving average lags price) are encoded in the market data indicators, not in the agent interaction model.
Horizon Batch projection. The system processes 6 stocks in a single run (~60–100s wall-clock with four LLM calls per stock). It looks backward 90–120 trading days for historical data but makes no forward projections. The output is a point-in-time snapshot of three strategy assessments plus three-way evaluator synthesis. Each run is one-shot — no continuous monitoring.
2 Structure Implementation
4
🔀 Orchestration & Organizational Architecture
Pattern Parallel fan-out with convergence. Sequential entry (Market Data) → parallel fan-out (three strategy agents) → convergence barrier → sequential exit (Evaluator → JSON save). Static DAG: one fork, one join per stock. Outer loop over stocks is sequential. Orchestration: plain Python asyncio in orchestration.py.
Static/Dyn Fully static. The agent roster (Market Data, three strategy LLMs including Volatility Averse, Evaluator), routing topology, and execution order are hardcoded. The ticker list is configurable in config.py; the pipeline shape is fixed.
Sync Two synchronization points per stock: (1) Data-ready barrier: all strategy agents wait for Market Data. (2) Strategy-complete barrier: Evaluator waits for all three strategy outputs. After the Evaluator completes, JSON is written and the next stock begins.
Adaptive No mid-execution adaptation. The pipeline never re-routes, re-scopes, or re-assigns agents. The only conditional logic is in the Evaluator's prompt: if agents agree, produce a consensus summary; if they disagree, produce a disagreement analysis. This is content-level branching within the Evaluator's response, not structural re-routing of the pipeline. If an LLM call fails after 3 retries, the pipeline records an ERROR and continues — it does not retry with a different agent or model.
5
📡 Communication Infrastructure
Mechanism Structured handoff via function return values. No message bus, no event queue, no blackboard. The orchestrator calls each component function, receives the return dict, and passes it as an argument to the next component. Communication is synchronous in-process data passing — the simplest possible mechanism for a single-machine batch pipeline.
Schema Market Data → Strategies: Python dict with ~25 typed fields (floats, ints, strings, lists) formatted into a natural-language user prompt string. Strategies → Evaluator: JSON dict with 4 fields: name (str), decision (enum: BUY|HOLD|SELL), confidence (int 1–10), justification (str 3–5 sentences). Evaluator → Output: JSON dict with 2 fields: agents_agree (bool), analysis (str 4–6 sentences). All schemas are enforced by the LLM prompt instructions + 3-layer parsing fallback in llm_client.py.
Protocol No interoperability protocol (MCP, A2A) — agents do not discover each other's capabilities at runtime. The orchestrator has hardcoded knowledge of all agents and their input/output contracts. This is appropriate for a fixed-roster, static-topology system where all components are co-located in one Python process.
6
🗄️ Environment & Grounding Infrastructure
Per Agent Market Data: yfinance API (read-only — historical OHLCV data, dividends, splits). Momentum Trader: Anthropic Messages API (write: sends system + user messages; read: receives assistant message). No other access. Value Contrarian: identical Anthropic access, different prompt. Evaluator: identical Anthropic access, comparative prompt. All LLM agents are pure inference endpoints with zero tool access.
Shared The computed market data dictionary is the sole shared knowledge artifact — produced once by Market Data and consumed identically by all three strategies and the Evaluator. The outputs/ directory is a shared write target mediated by the orchestrator. No shared vector store, no RAG index, no database.
Denied All agents are denied: web browsing, filesystem access (read or write), any API beyond yfinance and Anthropic, access to each other's system prompts, and any ability to execute trades or take external actions. The Market Data Component is specifically denied LLM access. The Evaluator is denied access to raw yfinance data (it receives only the pre-computed summary).
7
📐 Scale & Computational Architecture
Agent count Fixed at 4 components: 1 Market Data (non-LLM), 2 strategy agents (LLM), 1 Evaluator (LLM). No dynamic spawning. Each agent is instantiated as a Python function call — there are no persistent agent processes or agent pools. Per stock, the system makes exactly 3 LLM API calls (2 strategies + 1 evaluator). Total for 6 stocks: 18 LLM calls + 6 yfinance fetches.
Compute Single local machine (laptop/desktop). All computation is single-process Python. LLM inference is offloaded to Anthropic's cloud API. No GPU required locally. No elastic scaling — the system processes a fixed list of tickers and terminates. Estimated total runtime: ~50–75 seconds for 6 stocks.
Mapping All agents map to a single Python process. Strategy agents are logically parallel (asyncio.gather) but may appear sequential if the client serializes requests or hits rate limits. There is no process pool, no thread pool, and no container orchestration. The granularity is one function call per agent per stock — the finest possible.
Constraints Rate limit: Depends on Anthropic account tier and current API limits. The 2-second inter-stock delay reduces burst traffic. Token budget: ~800–1,200 tokens per strategy prompt (user + system), ~300–500 tokens per response. Cost: usage-based per Anthropic pricing. Memory: negligible — all data fits in a few Python dicts. No latency SLA — batch system tolerates variable API response times.

3 Collective Behavior & Quality
8
🤝 Coordination Strategy & Mechanism
Strategy Role-based with SOPs. Each agent has a fixed role defined by its system prompt (SOP). The Momentum Trader always applies trend-following logic; the Value Contrarian always applies mean-reversion logic. Roles never change, rotate, or adapt. Coordination is structural (pipeline topology) rather than strategic (no negotiation or Theory of Mind).
Execution The orchestrator routes the market data dict to three strategy functions, collects strategy_a/b/c JSON, and passes all three to the Evaluator. Fan-out/fan-in. No vote aggregation. The Evaluator produces narrative synthesis (three-way), not a single merged recommendation.
Decision No collective decision is made. The system does not resolve three outputs into one recommendation. All strategy outputs are preserved in JSON. The Evaluator explains convergence/divergence (including 2–1 splits) without crowning a winner.
9
🔍 Emergent Behavior Detection & Steering
Conflict Disagreement is detected by a simple string comparison: if strategy_a["decision"] != strategy_b["decision"], agents_agree = false. This boolean drives the Evaluator's prompt branching (consensus summary vs. disagreement analysis). Conflict is expected and valued — it is not a failure mode but the system's core output.
Circuit-break 3-retry limit per LLM call with 1-second backoff. If all retries fail, the system records {"decision": "ERROR", "confidence": 0} and continues the pipeline — the Evaluator receives the error and notes it. No max-iteration concern exists because there are no loops: each agent fires exactly once. The 2-second inter-stock delay acts as a passive circuit breaker for rate limiting.
Herd check Source independence: Strategy A/B/C cannot see each other's outputs — the orchestrator does not pass cross-strategy results. Prompts include explicit "ignore" lists. Post-run, summary.json records both Momentum–Contrarian agreement and whether all three match (`total_all_three_agree`).
Drift Behavioral drift is detected post-hoc by the analyst reviewing JSON outputs for: (1) personality leakage — a Momentum Trader citing contrarian reasoning, (2) justification-data disconnect — reasoning that doesn't reference the specific numbers provided, (3) schema drift — responses that deviate from the required JSON structure (caught by the 3-layer parser). No automated drift detection during execution.
10
✔️ Verification & Conflict Resolution
Evidence Agent justifications are verifiable against the market_data_summary saved in the same JSON file. A reviewer can check whether the specific numbers cited in a justification (e.g., "RSI of 72") match the computed indicators. The prompts require agents to reference ≥3 data points, making verification tractable. No automated verification is implemented — this is a human review step.
Separation JSON enforces separation: market_data_summary = facts; strategy_a / strategy_b / strategy_c = inferred judgments; evaluator = meta-judgment over three strategies (`agents_agree` for Momentum vs Contrarian, `agents_all_agree` for unanimity). Optional field `three_way_pattern` classifies unanimous vs 2–1 vs all distinct.
Contradiction Present both — no resolution. Contradictory recommendations are preserved side-by-side in the JSON output. The Evaluator explains the contradiction but does not resolve it. This is the correct architectural choice for this system: the goal is the quality of the disagreement analysis, not the correctness of a final recommendation. Forcing consensus would destroy the system's value.
Gaps If an LLM call fails completely (after 3 retries), the pipeline records an ERROR fallback dict and continues. The Evaluator receives the error state and can note it in its analysis. If yfinance returns insufficient data (< 90 days), a ValueError is raised and the stock is skipped with a console warning. Partial results are always saved — the system never silently drops a stock.
11
🎯 Calibration & Validation Protocol
Data feeds yfinance provides the sole data feed: daily OHLCV (open, high, low, close, volume) for each ticker over 120 calendar days. Known quality issues: yfinance may return adjusted vs. unadjusted prices depending on the query, weekend/holiday gaps require trading-day-only filtering, and data may lag by up to one trading day. RSI, moving averages, and volatility are computed locally from this data — no third-party indicator service.
Fit metrics No quantitative fit metrics apply — the system does not predict prices and is not measured on financial accuracy. Quality is measured qualitatively: (1) do justifications reference ≥3 real data points? (2) does the strategy pair produce ≥1 agreement and ≥1 disagreement across the stock set (6 tickers)? (3) does the Evaluator explain behavioral logic rather than restating decisions? These are quality criteria, not automated metrics.
Frequency No periodic recalibration — this is a one-shot batch system. "Calibration" is prompt tuning by the analyst between runs: run the system, inspect outputs, adjust system prompts in the text files, re-run. The prompt-loading-from-disk design enables this without code changes. A typical development cycle involves 3–5 calibration runs before final output generation.
Benchmarks No external model benchmark. The Momentum vs Contrarian pair cross-check each other; the third agent (Volatility Averse) adds a path-risk lens. If outputs collapse to identical reasoning, prompt design needs work. The comparative report is the validation artifact.
4 State, Planning & Trade-Offs
12
💾 State Management & Feedback Architecture
Shared Shared state is a Python dict passed by reference. The orchestrator holds market data and three strategy outputs in local variables. After JSON serialization to outputs/{TICKER}.json, in-memory state is discarded.
Private Each LLM agent's reasoning trace is private — it exists only within the Anthropic API call and is not logged or stored. System prompts are private per agent: the Momentum Trader's prompt is never shown to the Value Contrarian or the Evaluator. The Evaluator sees strategy outputs (decision, confidence, justification) but not the prompts that produced them.
Feedback No intra-run feedback loops. The only feedback path is human-in-the-loop between runs: analyst inspects JSON outputs → identifies weak prompts or generic reasoning → edits prompt text files → re-runs. This is a manual calibration loop, not an automated feedback architecture. The prompt-on-disk design explicitly supports this workflow.
Lifecycle Task-scoped. All in-memory state is created when a stock analysis begins, consumed during the pipeline, serialized to JSON, and discarded when the stock analysis ends. No state persists across stocks. The JSON output files persist on disk after the run terminates — they are the system's only durable artifact. No session state, no cross-run memory.
13
📋 Task Decomposition & Planning
Method Static decomposition. The pipeline is a fixed 4-step workflow per stock (fetch → analyze A ∥ analyze B → evaluate). This decomposition is hardcoded at design time, not planned dynamically by an LLM. The sub-tasks are the same for every stock — only the data changes.
Assignment Assignment is by role — fixed and deterministic. Market Data always fetches. Momentum Trader always runs strategy A. Value Contrarian always runs strategy B. Evaluator always synthesizes. There is no capability matching or load balancing because the roster is fixed and each role maps to exactly one component.
Assembly Aggregation into a structured JSON document. The orchestrator assembles the final output by nesting each component's output into a single dict: {ticker, run_date, market_data_summary, strategy_a, strategy_b, evaluator}. No merge conflicts are possible because each component writes to its own namespace in the output. The summary.json is a separate aggregation pass that extracts decision-level data from all per-stock JSONs.
Adaptive The plan cannot change mid-execution. No re-planning, no scope changes, no dynamic re-routing. If a component fails (LLM timeout), the system records an error and continues — it does not reassign the task to a different agent, retry with a different model, or modify the pipeline. Adaptivity is explicitly rejected in favor of simplicity and debuggability.
14
⚖️ Trade-Off Priorities
Priority 1 Behavioral clarity over financial accuracy. The system prioritizes clearly differentiated agent behaviors over producing "correct" investment advice. A system where agents disagree for well-articulated reasons is more successful than one where both agents happen to be right but produce identical reasoning. This is the system's core trade-off and the architecture is designed around it.
Priority 2 Simplicity and debuggability over sophistication. Plain Python over LangChain. Single-shot prompts over ReAct loops. Function calls over agent frameworks. Sequential stock processing over full parallelism. Every architectural decision favors the simplest approach that satisfies requirements. This minimizes debugging surface area and makes the system transparent to reviewers.
Accept Accepted limitations: LLM non-determinism (same inputs may produce slightly different outputs on re-run), no automated quality validation (human review required), no real-time data (batch snapshot only), no iterative refinement (single-shot prompts may miss nuance), and API rate limits (2-second delays between stocks). These are acceptable because the system is a learning exercise, not a production tool.
Reject Explicitly out of scope: dynamic agent spawning, cross-session memory, agent-to-agent dialogue (debate mode is an optional extension only), tool use by LLM agents, RAG/vector search, model fine-tuning, backtesting, portfolio optimization, multi-model heterogeneous setups, and any framework dependency beyond yfinance + anthropic + python-dotenv.
